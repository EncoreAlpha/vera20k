# VMCE 发展路线

本文记录已确定的目标、边界和验收顺序，供 DS 分阶段执行。当前已实现功能以[总览](vmce.md)和代码为准；具体缺陷与证据见[待办](vmce-todo.md)和[审查详情](vmce-review.md)。本文中的存档与互联网能力是未来目标，不表示已经实现。

## 目标与边界

VMCE 继续留在 VERA 同一仓库的 `feature/vmce` 独立分支并使用 VERA 引擎；当前代码仍由 `vmce` Cargo feature 控制，但目标是把游戏行为编译进普通构建，再由运行时状态决定是否启用。整个多人战役从大厅、选图、开局、任务中到结算、重试和续关，都由 VMCE 管理自己的战役规则和流程；VMCE 正式代码、测试和诊断工具最终均不直接或间接调用原版 Cooperative 专属流程。架构检查的禁止名单可以写 Cooperative 的名称。

这是按职责独立，不是把 Cooperative 代码改名或包一层再当成公共接口。允许 VMCE 单独维护相似的准备、确认和退出流程；上游修复 Cooperative 时，逐次检查是否适用，适用的修复单独移植和验证。避免为了独立而复制通用引擎规则或建立猜测性的通用框架。

- **VERA 继续负责：** 通用模拟规则、地图触发器与 House 胜负计时、网络会话和房主/玩家名单、可靠网络队列，以及按钮、文字等基础界面控件。共享入口可以保留明确的 VMCE 模式标记，并提供必要的通用能力。
- **VMCE 负责：** 自己的战役角色和流程决策、消息内容与离开时机、结算和续关状态，以及结算页内容、布局和操作。战役应用逻辑集中管理，网络和模拟扩展靠近各自所属层；每份权威状态仍只有一个所有者。
- **接入方式：** 共享 VERA 文件只做必要且清晰的接入或提供真正通用的能力。`sim/` 继续遵守不能依赖 `net/`、`app/`、`ui/` 等层的项目约束。
- **兼容与体验：** 保持现有玩法，结算页的可见布局和交互保持一致，允许细小像素差异。旧编译裁剪版、迁移桥版与最终运行时版的 LAN/WOL 互操作策略尚未决定，统一在 G4 调查；任务存档和本机关卡解锁仍按各自阶段决定兼容范围。战役格式与消息格式按需修改，不为改格式而改格式。不要主动删除已有用户数据。新版本各玩家的模拟结果必须一致，但不要求模拟校验和与旧版相同。

结算相关的流程已经分开：[vmce_round.rs](../../src/app/vmce_round.rs)、[session/vmce_result.rs](../../src/app/match_runtime/session/vmce_result.rs) 和 [LAN VMCE 服务](../../src/app/lan_service/vmce_round.rs) 持有 VMCE 自己的阶段状态、result agreement、Retry ACK 和关间交接；失败页由 [vmce_defeat.rs](../../src/app/frontend/skirmish_shell_render/vmce_defeat.rs) 独立绘制；结算统计的玩家行由 [vmce_result/statistics.rs](../../src/app/vmce_result/statistics.rs) 独占，原版 Cooperative 的结算行仍由 `sim/score.rs` 的 `cooperative_score_rows` 决定。大厅的模式事件也已分开：加入、退出、建房打开、选图（Use Map/Choose Map）、模式进入和选项解析的刷新由 [shell_network_setup/dispatch.rs](../../src/app/shell_network_setup/dispatch.rs) 按原生模式选择分派，VMCE 的槽位在 [vmce_setup.rs](../../src/app/shell_network_setup/vmce_setup.rs) 中，不再调用 Cooperative 专属入口；Cooperative 的 C0 由消息自身的安装身份归属（WOL 载荷模式或 LAN scope/revision），早到文本暂存到 HostSetup，旧/非 Cooperative 文本丢弃，VMCE 的模式事件不询问 Cooperative 的拥有者谓词。大厅其余部分也已进一步分开：阶段 3 第三个子链“共享大厅难度所有权”完成后，原生进程行 `[0xA8EB68]` 由 [MultiplayerShellRuntime](../../src/app/frontend/skirmish_session.rs) 类型化持有并在 LAN 接收边界归一，VMCE 开局冻结时取一次，加载 TriggerType 与结算页只读冻结值，Cooperative 读取同一所有者。大厅余下的 Cooperative 依赖和任务中接入仍属阶段 3 余下部分；已有的独立消息、战役数据所有者及 B10/B57 实现不代表整个模式已经独立。

## 取消 VMCE 游戏行为的编译期门控

这里的“取消门控”指取消游戏行为是否存在、能否解析、能否开始和能否运行的编译期差异；它不是把 `vmce` feature 改名，也不是把 VMCE 合并进 `main`。目标状态下，普通构建包含 VMCE 的类型、数据读取、网络字段、加载、模拟和界面，测试构建也能覆盖这些路径；运行时状态决定是否显示和许可一次 VMCE 开局；禁用状态的玩家可见行为仍是普通 VERA 与原版 Cooperative。

### 当前事实

截至 2026-11-14，`feature/vmce` 的首条“入口至开始许可”链已有候选实现，其他 VMCE 游戏行为仍保留编译期门控。首条链的运行时可用性由现有 [ScenarioCatalog](../../src/app/scenario_catalog.rs) 中已验证的 VMCE campaign 记录拥有，没有新增 INI 键、`RuleSet` 字段或第二份游戏状态。

- **注册：** [skirmish_modes.rs](../../src/skirmish_modes.rs) 在普通构建和 VMCE 构建中使用固定 VMCE 模式 ID；如果自定义模式占用该 ID，保留自定义模式并禁用 VMCE。feature-off 行保持 `lists_in_skirmish() == false`，原版 Cooperative 的 ID 3 不变。
- **解析与拒绝：** [LAN options](../../src/app/lan_service/options.rs) 在两种构建中都能把该 ID 解析为 VMCE；没有完整后端时，Options 预校验和 HostSetup 在改写共享会话前拒绝。旧已发布版仍只会走旧行为，本轮未修改联网协议。
- **可见与开始许可：** [房主选图](../../src/app/shell_skirmish.rs) 和 [开始回调](../../src/app/shell_network_setup/actions/start.rs) 从 catalog 记录派生“是否有 VMCE 入口”，并在没有可用入口或完整后端时隐藏/拒绝；模式行存在本身不再等于可开始。
- **仍未迁移：** `vmce_setup.rs`、VMCE 地图配置应用、加载、首帧模拟、结果和诊断等外围 `cfg` 仍在。它们是 G3 及后续范围；WOL 未在本轮新增支持。
### 职责拆分

| 职责 | 目标约定 | 禁止的混淆 |
|---|---|---|
| 注册 | 模式类、稳定身份和必要格式在所有构建中可构造、可解析；禁用只是状态 | 用“名单中没有 VMCE 行”代表不支持 ID |
| 可见 | 模式选择、`Maps/VMCE` 发现、相关按钮与文字由运行时可用性决定 | 让 UI 是否显示反向决定解析器是否存在 |
| 客机解析 ID | 新版客机能识别支持的 VMCE 身份并处理或明确拒绝相关字段；旧版不识别时通过兼容机制拒绝 | 把未知 ID 静默改写为普通模式 |
| 开始许可 | 房主以单一运行时许可汇总可用性、数据、模式和 LAN/WOL 能力；客人在 Ready/GO 前后复验同一结论 | 以“模式行可见”替代完整开局许可 |
| 运行执行 | 许可通过后才进入现有 VMCE 战役、轮次、加载和模拟所有者；失败在 GO 前给出可见原因 | 许可失败后仍进入部分 VMCE 状态或让对端等待到超时 |

本链的运行时启用来源已经确定为现有 `ScenarioCatalog` 的已验证 VMCE 条目集合；feature-off 迁移桥没有该 catalog reader，因此固定报告不可用。后续 G3+ 若需要新的配置或开关，必须另列数据合同、默认值、读取顺序和兼容性，不能从本链推定。

### 迁移阶段与停点

1. **G0：清单与决定（本链已完成）。** 已按“注册、可见、解析、许可、执行”分类首条入口链，确定 `ScenarioCatalog` 为运行时可用性 owner，并记录 feature-off、feature-on、旧发布版与 WOL 的边界。后续链仍按同一方法补清单。
2. **G1：身份与解析先编译（本链已完成候选）。** 模式类、ID 映射、`VmceSeries` 来源过滤和客机 ID 解析已在所有构建中存在；feature-off 仍不扫描、不显示、不允许开始，并在共享会话变更前拒绝 VMCE HostSetup。剩余 VMCE 协议/配置类型随 G3 迁移。
3. **G2：可见性与开始许可接入运行时状态（本链候选）。** 房主可见性和 `mode_start` 的 GO 前许可都读取同一个 catalog 可用性；feature-off 固定不可用。审查修复后的 feature-on 构建通过沙箱外本机双人胜利和续关；feature-off 客机及混合构建尚未实机验证。
4. **G3：完整 LAN 开始链迁移。** 让地图发现、配置交换、角色、Ready/MapStatus、`request_start`/`mode_start`、共享种子、加载与首帧模拟都不依赖编译期差异；禁用或数据不满足时在 GO 前明确拒绝。WOL 在 G4 决定前继续显式拒绝，不假称支持。
5. **G4：LAN/WOL 与旧新版本兼容决定。** 建立主机/客机矩阵：旧编译裁剪版、迁移桥版、最终运行时版；LAN 与 WOL 分开记录。无法解析、禁用、版本过旧和不支持 WOL 都必须在有界时间内给出可理解结果；若决定支持 WOL，还须证明地图/配置同步与 Ready/GO 身份一致。
6. **G5：退场。** 删除 `vmce` Cargo feature、迁移桥和游戏行为外围的剩余 `cfg`，用同一无 feature 构建验证禁用/启用两态。迁移过程中即可判断上游候选：只提交对上游有实际独立价值、可单独验证的最小能力；优先选择已有上游生产消费者的能力。

### 未确认项

| 项目 | 最晚决定阶段 | 完成条件 |
|---|---|---|
| 运行时启用来源与默认产品可见性 | G0，消费于 G2 | 基于现有数据和产品需要选定，不靠新增猜测键兜底 |
| VMCE 模式身份的碰撞与跨版本解析 | G1/G4 | 主机、客机与旧版对同一 ID 有确定结论，永不静默落到其他模式 |
| WOL 是否支持及所需配置同步 | G4 | 支持则完成 Ready/GO/身份验收；不支持则明确拒绝并记录能力边界 |
| 旧编译裁剪版、迁移桥版、最终版的互操作策略 | G4 | 明确拒绝或关闭功能，不能挂起、崩溃或错误开局 |
| 上游通用能力候选 | 迁移过程中逐项评估 | 对上游有独立价值并可单独验证；优先已有上游消费者，仅改名的 VMCE 代码不提 PR |

当前 `ModePolicy` 不是天然的“通用能力”：它仍含 `Vmce` 变体和仅 VMCE 语义。只有在抽出的字段确有上游非 VMCE 消费者时才拆分；给 VMCE 专用判断换一个泛化名字，不算通用能力。

## 阶段与停点

每个阶段按一条可玩的流程完成实现、验证和本地提交，DS 自审并报告结果后停下，等用户审查决定是否进入下一阶段。涉及游戏行为或在线联机时仍按项目规则进行只读 critic。独立完成并通过该阶段审查后，再处理与该阶段相关的已知问题；只有阻塞当前流程或可靠验收的问题可在独立阶段内修复。其他问题继续留在既有台账，不因为列入路线就视为已修复。

1. **上游同步审查（已完成）。** 审查 `89ccbea49` 的冲突解决、VMCE 必要功能与同步后验证记录，确认普通 VERA 和 VMCE 的边界以及未验证项；不再重复做已完成的上游合并。
2. **独立结算、重试和续关（已完成，审查修复后待审查）。** VMCE 自己拥有结果与关间流程的状态、决策和消息；独立失败结算页的内容、布局与操作，同时使用 VERA 基础控件。覆盖胜利进入下一关、失败重试、最后一关结束和退出；保留现有玩法及可见交互。上一轮已用双人本机多进程验收三个流程，并以自动测试覆盖丢包、ACK 丢失和对端无响应；原版 Cooperative 相关测试同时通过。残留风险见[基线](../vmce-baseline.md)。
3. **独立其余 LAN 战役流程（阶段 3；结算统计、大厅加入/退出与模式事件分派、共享大厅难度所有权三个子链已完成，其余未开始，当前停点）。** 分可玩的阶段处理建房、选图、角色、准备、开局和任务中接入，逐步移除对 Cooperative 专属代码的调用。2026-11-13 已完成两个子链：其一，VMCE 的结算统计按自己的角色/分配投影，Cooperative 保留自己的原版行选择，双方只共用 VERA 的 House 统计事实；其二，建房打开、加入、退出、选图、模式进入和选项刷新等大厅模式事件由共享分派所有者按原生语义选择模式（加入/退出在选图窗口打开时按窗口中选中的模式），VMCE 事件进入自己的槽位，不再经过 Cooperative 专属入口。其三，2026-11-14 完成共享大厅难度所有权：原生进程行 `[0xA8EB68]` 由共享大厅类型化持有，LAN 载荷保留原生字段名，VMCE 开局冻结时取一次、加载与结算只读冻结值，Cooperative 读取同一所有者。已增加针对真实边界的架构检查，并用双人本机多进程验收结算与大厅流程，详见[基线](../vmce-baseline.md)。其余流程仍待后续阶段，每阶段验证并停下审查，不把整个迁移包装成一次不可验收的大改。完成后核对正式代码、测试和诊断的直接及间接依赖，增加有针对性的架构检查并结合只读审查；最终整体验收补充三人、四人流程。
4. **取消 VMCE 游戏行为的编译期门控（规划）。** 按上文 G0–G5 和实际依赖推进，可与独立 LAN 流程按同一条可验收链协调进行；保留普通 VERA、原版 Cooperative 和现有 VMCE feature-on 路径。计划完成不等于实现或验证已经完成。
5. **LAN/本地任务中存档和载入。** 在 VMCE LAN 独立流程和编译期门控迁移完成后实现，具体规则见下文；先以双人本机多进程验证存档、退出、由房主载入、重选角色并继续操作。三人、四人及载入后打完任务和续关留待后续验收。
6. **互联网建房和开局。** LAN 独立、门控迁移与存档完成后，再按 G4 的决定接入现有 VERA 互联网大厅。第一步只供开发与测试，以模拟在线服务的自动测试和双人本机多进程验证建房、加入和开局；不面向玩家开放。互联网结算、重试、续关和存档传输在后续阶段实现并验证，完整战役流程完成后再考虑面向玩家提供。

## 任务中存档：已确定的规则

- 每名玩家可从现有暂停菜单入口手动创建多个命名本地存档，各人的保存时刻可不同。在一致的游戏时刻取得状态；允许保存者短暂卡顿，但不能触发全体暂停。暂不做自动存档。
- 载入先返回房间，由房主选择自己的存档；其他玩家加入后使用这份共同游戏状态。允许更换玩家，重新选择存档已有角色，可随机分配未占用角色，不能重复占用。房主可在 LAN 或本地单人继续；未被选中的角色保留原有单位与地图触发器，但无人控制，不自动交给 AI。
- 视野、已探索地图及击杀、损失、收入等战绩跟随所选角色。保留存档时的难度和游戏规则，只重新分配角色。按当前玩家所选角色和地图联盟计算胜负：至少一名当前玩家获胜才能进入下一关；无人控制角色的地图触发器仍按原地图规则执行。
- 各玩家事先安装相同战役和规则并在载入前校验，网络只需传送共同游戏状态。传输或校验失败时，全员返回载入房间，显示原因，修复后可重试。载入前在房间加入和选角色；对局开始后暂不支持中途加入、重连、直接回档或新增房主迁移，离房按现有 VMCE 行为处理。
- 实现时核对完整模拟状态、各角色视野、角色授权和联机同步的恢复边界；不能用只含当前玩家视图的展示投影代替完整状态，也不能把房主的本地镜头、选择等界面状态套给所有玩家。同一平台载入是本轮要求，跨平台存档暂不要求。

## 互联网：已确定的规则

- 通过 VERA 现有互联网大厅手动建房、加入并选择多人战役，所有玩家预装并校验相同战役和规则。VMCE 版与普通 VERA 的互联网房间互相隔离、互不可见；LAN 房间与互联网房间也各自独立。暂不做自动匹配。
- 互联网房间至少两名真人；单人继续仅走 LAN 或本地。先验证同平台双人；真实跨机器、三人和四人验收留到后续。新增界面提供中英文，其他语言可暂用英文。
- 只改客户端，不修改或部署大厅/中继服务。互联网载入需要自动传输房主存档；现有地图传输有大小和用途限制，不能假设它已能传输任意存档。如果现有客户端和服务无法可靠支持，报告具体阻碍，不以手工复制代替自动传输，也不宣称该功能完成。

## 全程验收与交付约束

- 迁移桥阶段分别检查普通构建与 `--features vmce` 构建，保证普通 VERA 和原版 Cooperative 路径不变；最终阶段在无 `vmce` feature 的同一构建中验证运行时禁用与启用两态。新代码的网络协议、持久化和模拟权威状态按项目契约验证。
- 本轮不要求 20,000 单位性能测试、不要求 VMCE 与 Ares 组合验收、不要求跨平台互联；这些不改变 VERA 支持的平台和通用确定性约束。
- 用户尚未授权发布、推送或合并远程；每阶段只在本地提交并报告。上游同步已完成，独立期间只处理必要的上游变化；若发生真实玩法冲突，交用户决定。
